## 1. Назначение, режим работы, единица решения

### 1.1. Цель

On-device инструмент, который при наборе текста определяет, что пользователь печатает не в той раскладке, и заменяет символы на корректные, используя детерминированный маппер QWERTY ↔ ЙЦУКЕН.

Пример: `ghbdtn` → `привет`.

### 1.2. Ключевые ограничения

- **Модель не генерирует текст.** Выход — распределение по фиксированному набору классов. Любая генерация свободного текста запрещена (см. раздел 10).
- **Замена выполняется детерминированным маппером**, а не моделью. Маппер — фиксированная таблица соответствия скан-кодов клавиш, не обучаемый компонент.
- Все вычисления — локально. Сетевые вызовы при инференсе запрещены.

### 1.3. Единица решения (новое требование)

Решение принимается **на границе слова** — по событиям: пробел, табуляция, Enter, знаки пунктуации, потеря фокуса, конец сегмента ввода. Посимвольное решение (на каждом нажатии) не допускается как основной режим: оно даёт нестабильные промежуточные вердикты и мигание текста на экране.

Допускается **ранняя детекция** внутри слова при выполнении всех условий одновременно:
- не менее `EarlyDetectionMinChars` символов набрано (значение — в разделе 8.7);
- уверенность выше `ConfidenceAtMinChars`;
- условие `ConsecutiveAgreementCount` выполнено `N` подряд идущих шагов.

Ранняя детекция не должна срабатывать на слове короче 4 символов.

### 1.4. Определение «слова» (уточнение п. 7.6 исходника)

Слово — максимальная последовательность символов одного скрипта, ограниченная символами из набора разделителей: пробел, табуляция, перевод строки, а также Unicode-категории `P*` (пунктуация) и `S*` (символы), за исключением символов, входящих в состав e-mail, URL, десятичных чисел и путей к файлам. Требуется явная реализация исключений для шаблонов `\S+@\S+`, `https?://\S+`, `[A-Za-z]:\\\S+`, `\.{1,2}/\S+`, `\d+([.,]\d+)?`.

### 2.1. Бюджет задержки

Требование `>0,0001 ms` из исходной версии невыполнимо: 100 наносекунд меньше времени вызова любой функции инференса. Заменяется на измеримые бюджеты:

| Сценарий | Бюджет p95 | Бюджет p99 |
|---|---|---|
| Статистический слой (lookup LM + словарь), без нейросети | ≤ 50 мкс | ≤ 200 мкс |
| Полный пайплайн с нейросетью-арбитром, CPU | ≤ 5 мс | ≤ 15 мс |
| Полный пайплайн с нейросетью-арбитром, Core ML | ≤ 3 мс | ≤ 10 мс |

Метрика измеряется **от события нажатия клавиши до завершения вставки исправленного текста**, а не только инференс. Измерения — на целевых устройствах, не на сервере. Обязательно фиксировать: модель устройства, ОС, число используемых потоков CPU.

## 3. Архитектура решения

### 3.1. Общая схема

Пайплайн состоит из трёх уровней, вызываемых последовательно с ранним выходом:

```
[событие клавиатуры]
      ↓
[буфер слова / окна 20 символов]
      ↓
[Уровень 1: статистика]
   карты маппинга + n-gram LM + частотные словари
      │
      ├── уверенный вердикт (счёт отрыва выше порога) → [маппер] → замена
      │
      └── неуверенный вердикт
             ↓
      [Уровень 2: нейросеть-арбитр] (char-CNN или 2-слойный Transformer)
             ↓
      [Уровень 3: калибровка + пороги по длине]
             ↓
      [маппер] → замена  ИЛИ  без изменений
```

### 3.2. Уровень 1 — статистический слой

Для входного слова `w` строятся две гипотезы:

- `H_asis` — слово остаётся как есть;
- `H_map` — слово после применения маппера раскладки.

Для каждой гипотезы считается логарифм правдоподобия по char-n-gram модели соответствующего языка (рекомендуется порядок 4–5, сглаживание Witten–Bell или Kneser–Ney) плюс бонус за наличие в частотном словаре.

Решение принимается при выполнении одновременно:
- разность `Δ = score(H_map) − score(H_asis)` превышает порог `Δ_min`;
- `score(H_map)` превышает минимальный абсолютный порог `S_min`.

Если условия не выполнены — слово передаётся арбитру либо остаётся без изменений.

### 3.3. Уровень 2 — нейросетевой арбитр

Вызывается **только** для слов, не разрешённых статистикой (оценочно 5–15% случаев). Это ключевое проектное решение: оно снимает требование к пропускной способности сети.

### 3.4. Компоненты, поставляемые с моделью

1. Таблица маппинга QWERTY ↔ ЙЦУКЕН (по скан-кодам, не по символам). Учитывает: `ё` (`` ` ``), `ъ` (`]`), `ь` (`m`), `ж` (`;`), `э` (`'`), `х` (`[`), `б` (`,`), `ю` (`.`), `.` (`/`).
2. Частотные списки слов RU и EN с численностями.
3. Char-n-gram LM RU и EN (сериализованные таблицы).
4. Обученный чекпоинт арбитра.
5. Пользовательский словарь исключений (локальный, шифрованный).

## 5. Спецификация нейросети-арбитра

### 5.1. Обоснование изменения архитектуры

Исходная спецификация: ensemble (multi-scale CNN + Transformer), 4 слоя, d=256, 4–8 голов, 1–5M параметров.

Проблема: при d=256 и 4 слоях модель содержит ~3M параметров и требует ~120 MFLOPs на окно 20 символов. Это 0,5–2 мс на CPU в один поток — без учёта статистического слоя, калибровки и вставки текста. Плюс ensemble удваивает стоимость. Для задачи классификации окна из 20 символов в 5 классов это избыточно.

### 5.2. Базовая конфигурация (по умолчанию)

| Параметр | Значение |
|---|---|
| Тип | char-CNN |
| Эмбеддинг | 32, обучаемый |
| Свёрточные блоки | 3 блока с ядрами 3, 5, 7; каналы 64, 128, 128 |
| Активация | ReLU или GELU |
| Нормализация | без BatchNorm; LayerNorm при нестабильности |
| Пулинг | global max pooling + global average pooling, конкатенация |
| Dropout | 0.1 |
| Классификационная голова | Linear → 5 классов |
| Параметров | ~0,1–0,3M |
| Окно | 20 символов |

### 5.3. Альтернативная конфигурация (для сравнения)

| Параметр | Значение |
|---|---|
| Тип | char-Transformer (encoder-only) |
| Слоёв | 2 |
| Hidden size | 128 |
| Голов | 4 |
| FFN hidden | 256 |
| Позиционное кодирование | синусоидальное или RoPE |
| Параметров | ~0,3M |

### 5.4. Расширенная конфигурация (только для сравнения, не для продакшена)

Спецификация из исходника: 4 слоя, d=256, 4–8 голов, ensemble CNN+Transformer. Допускается к реализации **исключительно** как контрольная точка на этапе исследования. В продакшен переходит только если её precision срабатывания выше базовой на ≥ 0,3 п.п. при соблюдении бюджета задержки.

### 5.5. Токенизация

Character-level. Словарь: строчные и прописные латинские буквы, строчные и прописные кириллические буквы (включая `ё`, `Ё`), цифры 0–9, распространённые разделители и знаки, символ «вне словаря» (UNK). Итого ~130–160 токенов. Токенизация должна сохранять регистр — регистр несёт информацию.

### 5.6. Что запрещено в архитектуре

- Использовать генеративную LLM (GPT, Llama, Qwen и любые seq2seq/LM-декодеры) в любой форме.
- Использовать любую голову, порождающую последовательность.
- Использовать словарный подход как **единственный** метод.

### 5.7. Все компоненты ансамбля (если он реализуется)

«Пулинг обоих потоков в единый linear head» из исходника подлежит уточнению: признаки CNN и Transformer объединяются **конкатенацией** после независимого усреднения по времени, размерность конкатенации приводится линейным слоем к размеру головы. Альтернативный вариант — две головы с усреднением logits; выбор фиксируется после абла́ции.

## 6. Датасет

### 6.1. Исключённый источник

Датасет `anzorq/kbd_lat-835k_ru-3M` **исключается**. Расшифровка: `kbd` — код языка кабардинский (ISO 639-3, Kabardian), `lat` — латинская письменность. Датасет содержит «835k строк кабардинской латиницы + 3M строк русского из Wiki (OPUS)». Кабардинская часть для задачи RU↔EN бесполезна; русская часть избыточна при наличии собственных источников. Использование этого датасета в исходном ТЗ — следствие неверной расшифровки `kbd` как «keyboard».

### 6.3. Формирование примеров

1. Чистый русский текст → маппер в EN → метка `ru_from_en`.
2. Чистый английский текст → маппер в RU → метка `en_from_ru`.
3. Чистый русский текст → метка `ru`.
4. Чистый английский текст → метка `en`.
5. Код, URL, e-mail, числа, пути, транслит → метка `neutral`.

Окно формируется вокруг последнего слова; контекст заполняется реальными соседними словами того же текста, а не случайными символами. Окна короче 20 символов дополняются маркером начала/конца последовательности, а не пробелами.

### 6.4. Обязательные негативы (критично для FP rate)

- **Транслит:** `privet`, `spasibo`, `kak dela`, `horosho`.
- **Техническая латиница:** `kubectl`, `npm`, `git`, `iOS`, `API`, `UUID`, `localhost`.
- **Двусмысленные короткие слова**, у которых обе гипотезы правдоподобны. Для пары EN→RU это слова вида `lf`→да, `ds`→вы, `gj`→по, `gh`→по. Для пары RU→EN — `да`→lf, `вы`→ds. Таких пар — сотни; требуется явный список, составленный по пересечению частотных словарей.
- **Смешанные окна:** RU-контекст + последнее слово в EN, EN-контекст + последнее слово в RU.
- **Верхний регистр и Caps Lock:** `GHBDTN` → `ПРИВЕТ`, `Ghbdtn` → `Привет`.
- **Пунктуация на границах слова.**

### 6.5. Аугментация

| Метод | Применять | Комментарий |
|---|---|---|
| Опечатки (пропуск, дублирование, перестановка) | Да | Малой долей, ≤ 5% примеров |
| Смена регистра | Да | Обязательно, иначе модель не увидит `GHBDTN` |
| Label smoothing | Да | См. раздел 7 |
| Смешанные параграфы | Да | Иначе модель не обучится на смешанный ввод |
| Mixup на эмбеддингах | **Условно** | На дискретных символах размывает границу `ru_from_en` / `neutral`. Включать только при доказанном выигрыше на валидации; в базовом рецепте — выключен |

### 6.6. Объём и баланс

| Сплит | Объём | Состав |
|---|---|---|
| Train | 3–10M примеров | Все классы; доля `neutral` 25–35% |
| Validation | 300–500K | Стратифицировано по классу и длине слова |
| Test (синтетический) | 300–500K | Несбалансирован: акцент на код, URL, имена |
| Test (реалистичный) | 5–20K | **Набран вручную или собран из реального ввода.** Обязателен |

**Синтетический тест не является достаточным основанием для приёмки.** Реалистичный сплит — обязателен, иначе метрики FP rate завышены систематически.

### 6.7. Приватность данных

- Логирование пользовательского ввода на диск без явного согласия запрещено.
- Поля с атрибутом `secure` и режимом «пароль» исключаются из обработки полностью (не только из логирования).
- Данные для реалистичного теста собираются с информированного согласия и анонимизируются (хеширование идентификаторов, удаление имён, адресов, телефонов, ключей).
- Пользовательские исключения (см. 8.3) хранятся локально в шифрованном виде.

### 7.1. Label smoothing и пороги: обязательный учёт

Label smoothing снижает максимальную достижимую уверенность модели и делает её распределение «плоским». При smoothing 0.1 и 5 классах целевая вероятность правильного класса в пределе равна `0.9 + 0.1/5 = 0.92`, а не 1.0. Порог принятия 0.9, заданный константой, при таком обучении будет срабатывать реже, чем предполагалось, а сам смысл порога станет неоднозначным.

**Требование:** после обучения обязательна процедура temperature scaling на валидации (см. 7.2), после чего пороги подбираются уже по калиброванным вероятностям.

### 7.2. Калибровка (обязательный этап)

1. Обучить модель.
2. На валидации, не пересекающейся с train, подобрать температуру `T > 0`, минимизируя NLL калиброванных вероятностей `softmax(logits / T)`. Temperature scaling не меняет argmax, то есть не влияет на accuracy.
3. Зафиксировать `T` в артефактах и применять при инференсе до сравнения с порогом.
4. Построить reliability diagram и посчитать ECE отдельно по каждому классу и каждому бину длины.

**Особенность:** при малой или несмещённой по классам валидационной выборке классический temperature scaling может остаться смещённым по миноритарным классам. Контрмера: стратифицировать валидацию по классу, посчитать ECE по классам отдельно, при расхождении — применить class-wise температуры `T_k`.

### 7.3. Воспроизводимость

Обязательно фиксировать и поставлять в артефактах: версии PyTorch, torchvision (если используется), coremltools, ONNX Runtime, onnx, Python; хеш датасета; хеш таблицы маппинга; seed; полный конфиг обучения.

## 8. Выходные пороги и поведение в рантайме

### 8.1. Базовое правило

Слово заменяется, только если:
- предсказанный класс — `ru_from_en` или `en_from_ru`;
- калиброванная уверенность ≥ порога, зависящего от длины слова;
- слово не входит в список исключений (8.3);
- ввод не находится в чёрном списке полей (8.4).

Во всех остальных случаях — без изменений.

### 8.2. Порог по длине слова (замена константы 0.9)

Порог определяется таблицей, подобранной на валидации по критерию «FP rate ≤ целевого при максимальном recall»:

| Длина слова (символов) | Порог `t(L)` (стартовое значение) |
|---|---|
| 1–2 | не исправлять никогда |
| 3–4 | 0.97 |
| 5–7 | 0.94 |
| 8–12 | 0.90 |
| 13–20 | 0.86 |

Значения — **стартовые ориентиры**, подлежат пересчёту на данных проекта. Логика: короткое слово несёт мало информации, поэтому требует более высокой уверенности.

### 8.3. Learned exceptions

Если пользователь отклонил замену для слова, слово запоминается (case-folded) как исключение и повторно не исправляется. Требования:
- хранение локальное, шифрованное;
- есть лимит на размер списка (рекомендуется 10 000 записей, вытеснение по давности);
- есть команда полной очистки списка.

### 8.4. Чёрный список контекстов

Модель **отключается** (не запускается вообще) в:

- полях с атрибутом `secure` / `password` (на уровне перехвата определить такую возможность не всегда удаётся; обязательно блокировать в браузерных расширениях и полях с явной разметкой);
- окнах терминалов и консолей по идентификатору приложения;
- редакторах кода и IDE по идентификатору приложения либо по языку подсветки;
- полях ввода команд, поиска по репозиториям, адресных строк браузера (по решению продукта).

### 8.5. Отмена (Undo)

После замены пользователь может отменить её в течение 10 секунд (клавиша Esc либо настраиваемая). Буферизуется не менее 100 символов после позиции замены. Отмена сбрасывается при: клике, смене фокуса, Enter, стрелках навигации, ручном переключении раскладки, истечении таймера.

### 8.6. Поведение при неуверенности

Если уверенность ниже порога — **текст не изменяется**. Подача подсказки (например, неблокирующий визуальный намёк) допустима как отдельная опция, включённая по умолчанию выключенной, и не должна менять текст.

### 8.7. Пер-языковые и ранняя детекция

Для пар `en→ru` и `ru→en` — раздельные наборы: `EarlyDetectionMinChars`, `ConfidenceAtMinChars`, `ConfidenceAtMaxChars`, `ConsecutiveAgreementCount`. Значения подбираются независимо для каждой пары на валидации.

## 9. Метрики приёмки

### 9.1. Главная метрика

**Precision срабатывания** — доля правильных замен среди всех выполненных замен. Пользователь переносит пропущенную ошибку легче, чем испорченный текст. Порог: **≥ 99,5%** на реалистичном тесте.

### 9.2. Полный набор метрик

| Метрика | Порог | Условие измерения |
|---|---|---|
| Precision срабатывания (общая) | ≥ 99,5% | Реалистичный тест |
| Recall срабатывания (общая) | ≥ 97% | Реалистичный тест |
| Overall accuracy (5 классов) | ≥ 99,0% | Синтетический тест |
| Accuracy класса `neutral` | ≥ 99,5% | Отдельный подсчёт на нейтральных данных |
| FP rate на коде/URL (на 1000 вхождений) | ≤ 0,1 ложных на 1000 | Отдельный набор `kubectl`, `github.com`, `npm install`, `user@example.com`, `https://` |
| FP rate на 1000 введённых реальных слов | ≤ 1 | Реалистичный тест |
| Accuracy по длине слова: 3–4 / 5–7 / 8+ | ≥ 95% / ≥ 98% / ≥ 99% | Стратифицированный подсчёт |
| ECE (после калибровки) | ≤ 0,02 | По каждому классу отдельно |
| Задержка p95 полного пайплайна | ≤ 5 мс | На целевом устройстве |
| Задержка p95 статистического слоя | ≤ 50 мкс | На целевом устройстве |
| Доля отмен (Esc-undo) | ≤ 0,5% от всех замен | Прокси реального FP в проде |
| Размер модели на диске | ≤ 5 МБ | Все артефакты без словарей; словари отдельно |

### 9.3. Метрики, которые не применяются

BLEU, perplexity, ROUGE, METEOR, chrF и любые генеративные метрики — для классификации раскладки бессмысленны.

### 9.4. Критерий отказа от нейросети (обязательная проверка)

Перед приёмкой обязательно сравнение полного пайплайна с одним статистическим слоем (без арбитра). Нейросеть сохраняется в продакшене, только если она даёт прирост precision или recall на реалистичном тесте **не менее 0,3 п.п.** При меньшем приросте — нейросеть убирается, продукт поставляется на статистике. Это снижает сложность, задержку и риск ошибок.

## 10. Квантование, сжатие и деплой

### 10.1. Изменение требований

Исходное ТЗ предписывало: mixed INT4/INT8, INT4 на ранних свёрточных слоях, INT4-палеттизация на ~50–60% моделей, размер 14–20 МБ, профилирование через `get_weights_metadata`.

Проблемы:

1. **Арифметика не сходится.** 1–5M параметров в INT4 — это 0,5–2,5 МБ. 14–20 МБ соответствует модели ~7–10M параметров в FP16. Либо архитектура из исходника больше заявленной, либо цифра размера взята из другого расчёта.
2. **INT4 для такой сети экономит мало.** При 0,2 МБ весов в FP16 экономия памяти несущественна, а ускорения на CPU не будет вообще: ядра CPU для 4-битных операций не оптимизированы. Выигрыш возможен только на Neural Engine.
3. **Core ML: эффект модель-зависим.** По документации Apple, 4-битная палеттизация даёт ускорение от 5% до 30% на Neural Engine — диапазон, заявленный самой Apple, и он зависит от модели и железа. Для сети < 1M параметров оверхед вызова Core ML может оказаться больше абсолютного времени инференса.

### 10.2. Требуемая процедура

1. Обучить модель, экспортировать в ONNX FP32.
2. **Сначала замерить**, не оптимизировать:
   - задержка FP32 на CPU (1 и 4 потока);
   - задержка FP16;
   - задержка при `computeUnits = .cpuOnly` в Core ML;
   - задержка при `.all` (с Neural Engine);
   - доля времени, приходящаяся собственно на инференс, а не на оверхед вызова.
3. Если базовые задержки укладываются в бюджет раздела 2 — **квантование не применять**. Это наиболее вероятный исход для сети < 0,3M параметров.
4. Если не укладываются — применять в порядке возрастания риска:
   - INT8 (dynamic quantization в ONNX Runtime; weight-only 8-bit в Core ML) — потеря точности минимальна, риск низкий;
   - 8- или 6-битная палеттизация в Core ML;
   - 4-битная палеттизация — только с per-layer профилированием чувствительности.
5. Для **каждого** варианта сжатия обязательно повторное измерение precision/recall срабатывания. Критерий: падение precision не более 0,2 п.п. При большем падении вариант отклоняется.
6. Результат — таблица «вариант сжатия → размер → p95 задержки → precision/recall». Решение принимается по ней.

### 10.3. Что сохраняется из исходника

- Требование профилировать чувствительность по слоям перед квантованием — сохраняется.
- Формат Core ML для macOS/iOS, ONNX для Windows/Linux — сохраняется.
- Запрет на INT4 всех слоёв без профилирования — сохраняется.
- Отдельная обработка attention-слоёв при квантовании (они чувствительнее свёрточных) — сохраняется.

### 10.4. Альтернатива квантованию

Дистилляция статистического слоя в нейросеть (или нейросети в ещё меньшую нейросеть) даёт, как правило, больший выигрыш «размер ↔ качество», чем квантование. Рассмотреть как приоритетную оптимизацию, если базовой конфигурации не хватает.

## 12. Что категорически запрещено

1. Использовать генеративную LLM (GPT, Llama, Qwen и любую другую) в любой форме.
2. Позволять модели «додумывать», продолжать или перефразировать текст.
3. Использовать словарный подход как единственный метод — он ломается на именах, коде, URL, аббревиатурах.
4. Применять INT4 ко всем слоям без per-layer профилирования.
5. Оценивать качество через BLEU / perplexity / ROUGE.
6. Принимать модель по метрикам только на синтетическом тесте.
7. Логировать пользовательский ввод на диск без явного согласия.
8. Принимать решение посимвольно (на каждом нажатии) как основной режим.
9. Хардкодить глобальный порог уверенности без зависимости от длины.
10. Пропускать этап temperature scaling при обучении с label smoothing.

## 14. Открытые вопросы, требующие решения до старта

1. Есть ли возможность собрать реалистичный тестовый набор 5–20K набранных слов? Без него приёмка по FP rate некорректна.
2. Нужен ли режим автопереключения раскладки ОС (не только замена текста) — и есть ли к нему доступ на целевых платформах?

4. Нужны ли иные языковые пары помимо RU↔EN (например, RU↔UK, RU↔DE)? От этого зависит обобщённость маппера.
5. Кто владелец корпуса пользовательских исключений и как обеспечивается его удаление по запросу?
6. Требуется ли поддержка Wayland (там перехват клавиатуры ограничен) и если да — достаточно ли уровня «замена по выделению»?
