# Оценка оптимальности решений ТЗ v3 — 2026-10-29

**Основа:** нормативная редакция layout-corrector/spec/TZ_layout_correction_v3.md в ветке claude/layout-corrector-spec, reference engine и conformance tests. Внешняя проверка: документация Microsoft и Apple, публичные README реализованных macOS-переключателей раскладки.

## Вывод

**Фундаментально менять ML-архитектуру не рекомендую.** Маленький CNN, статистический baseline, строгая калибровка, таблица приоритетов, default-deny и условие EV-12 — разумная и экономная конструкция. Нет оснований увеличивать сеть, внедрять ансамбль или заниматься INT8/4-bit до измерений на целевых устройствах и реальных данных.

Но есть несколько улучшений с существенной инженерной ценностью. Самое важное — не пытаться обеспечить одинаковую гарантию сохранности текста для двух принципиально разных способов замены.

## 1. Самое полезное улучшение: разделить возможности замены по уровню гарантий

### Что не оптимально сейчас

ТЗ предпочитает M1 — замену диапазона через текстовый интерфейс — и разрешает M2 — синтетические Backspace/Unicode-события — для части приложений. Но в §13.2 для M2 прямо признано, что гонку с физическим вводом нельзя предотвратить, а безопасный откат в некоторых случаях невозможен. Одновременно RT-4 требует ноль невосстановленных инцидентов, а текст гарантии звучит безусловно.

Это не только недоработка документа. Это ограничение архитектуры: наблюдатель видит событие уже после того, как оно было передано приложению; между чтением текста, заменой и проверкой может произойти другое действие пользователя или целевого приложения.

Официальная документация Microsoft подтверждает, что UI Automation TextPattern предназначен для чтения текста и сам по себе не предоставляет операцию его изменения; запись зависит от других интерфейсов и возможностей конкретного контрола ([Microsoft: TextPattern Overview](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-textpattern-overview), [UI Automation text object model](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-understandingtheuiautomationtextobjectmodel)). Это объясняет, почему универсальная атомарная замена во всех Windows-приложениях недоступна через один API.

### Более устойчивое решение

Ввести в runtime не просто пометку приложения M1/M2, а **формальные возможности адаптера**:

- READ_RANGE — прочитать текст вокруг каретки;
- REPLACE_RANGE — заменить конкретный диапазон через поддерживаемый текстовый интерфейс;
- READBACK — проверить фактический результат;
- ROLLBACK — восстановить исходный текст, если проверка не прошла;
- SYNTHETIC_INPUT — запасной путь через искусственные события.

Автоматическая коррекция по умолчанию включается только там, где есть проверяемая процедура замены и восстановления. Для M2 без надёжного отката безопаснее оставить MANUAL_ONLY или сделать его отдельным явным режимом с более узкой гарантией. Не следует одновременно обещать безусловное отсутствие повреждения текста и разрешать путь, для которого откат может быть невозможен.

**Компромисс:** M1-only ограничит число приложений с автоматической коррекцией. Но это честнее, чем расширять список поддерживаемых приложений ценой неравной гарантии целостности. M2 можно включать по конкретному приложению только после проверки и только если критерий RT-4 действительно достижим.

### Что говорят существующие проекты

[Traple](https://github.com/spendolas/traple) на macOS использует CGEventTap, буферизует физические коды клавиш и вставляет исправленный текст; в проекте есть чёрный список приложений и переключаемые способы вставки. [SimpleSwitcher](https://github.com/VAndr/simple-switcher) использует Accessibility API и инъекцию Backspace/замены, с исключениями по приложениям. Эти проекты подтверждают практичность схемы «наблюдатель + ограничение приложений + ручная конвертация», но их README не дают оснований считать симуляцию ввода атомарной или гарантированно безопасной во всех контекстах. Поэтому я бы не копировал их fallback-механику без ограничений.

### Альтернатива для будущего релиза

Если приоритет — более надёжная правка текста, а не максимально широкий глобальный охват, стоит отдельно сделать spike на нативную интеграцию с текстовым сервисом. В Windows Text Services Framework предоставляет работу с текстовым контекстом через edit sessions и текстовое хранилище ([Microsoft: TSF](https://learn.microsoft.com/en-us/windows/win32/tsf/why-use-text-services-framework), [Text Stores](https://learn.microsoft.com/en-us/windows/win32/tsf/text-stores)). Это не бесплатная замена: требуется другая интеграция и совместимость зависит от приложения. Поэтому я не предлагаю переносить туда весь v1 до прототипа, а лишь проверить, даст ли TSF заметный выигрыш на Windows для сложных редакторов.

## 2. Windows: точнее распознавать раскладку и проверить альтернативу глобальному hook

### Точный идентификатор раскладки

В §13.7 текущая схема сравнивает младшее слово GetKeyboardLayout с 0x0409/0x0419. По документации Microsoft, младшее слово HKL содержит LANGID, а верхнее относится к физической раскладке; язык ввода вообще может обозначать не только раскладку клавиатуры, но и иной input method. Для таблицы физического преобразования одного признака «английский/русский» недостаточно ([Microsoft: GetKeyboardLayout](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardlayout)).

**Лучше:** разрешать автоматическую коррекцию только для точно известных поддерживаемых идентификаторов/вариантов раскладки. На неизвестной раскладке — OFF/UNKNOWN. Проверять не только первичную конфигурацию, но и изменения раскладки во время сессии.

### WH_KEYBOARD_LL или Raw Input

Microsoft предупреждает, что низкоуровневый hook должен возвращаться быстро; при timeout в Windows 7+ он может быть незаметно удалён. В документации отдельно сказано, что в большинстве случаев следует рассматривать Raw Input как альтернативу ([Microsoft: LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc), [Hooks overview](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-hooks)).

Это не означает, что Raw Input точно лучше для данного продукта: у него нужно проверить получение событий в фоне, соотношение с фокусом и раскладкой, работу с модификаторами и различие физических и синтетических событий. Но **до закрепления WH_KEYBOARD_LL как единственного Windows-механизма стоит провести короткий сравнительный прототип**. Критерии — надёжность событий, работа с поддерживаемыми приложениями, CPU, задержка callback и восстановление после сбоев.

Если оставить hook, добавить отдельное требование на обнаружение потери потока событий и восстановление состояния. На macOS следует обрабатывать tapDisabledByTimeout / tapDisabledByUserInput: Apple документирует эти состояния ([Apple: tapDisabledByTimeout](https://developer.apple.com/documentation/coregraphics/cgeventtype/tapdisabledbytimeout)). После повторного отключения лучше уходить в безопасное состояние и уведомлять пользователя, а не продолжать считать hook работающим.

## 3. План приёмки: отличить proxy-gate от релизного gate

В плане работ G2 (§16.1) говорится, что baseline должен пройти EV-1 на синтетическом наборе, хотя нормативный EV-1 (§11.2–11.3) измеряет ложные коррекции на реальном R-ACC. Синтетический набор подходит для регрессии и первичного сравнения, но не доказывает частоту ложных исправлений на естественном вводе.

**Лучше:** назвать G2 предварительным proxy-gate с отдельными метриками. EV-1 и финальный EV-12 считать пройденными только после калибровки на R-CAL и оценки на замороженном R-ACC. Это защищает от ошибочного вывода «модель безопасна» до сбора настоящего теста.

Отдельно в §11.3 кластерная формула честно названа инженерным правилом без точного покрытия доверительного интервала, тогда как в таблице EV-1 есть формулировка «cluster-adjusted 95% upper bound». Лучше везде одинаково называть это **консервативным приёмочным критерием**, а не формальным 95%-м доверительным интервалом, если авторы не доказывают его статистическое покрытие. Сам критерий можно оставить; нужно только точно описать, что он гарантирует, а чего не гарантирует.

## 4. Калибровка: оставить простую формулу в v1

В §10.1 сказано: temperature scaling использует одно скалярное T, но при расхождении reliability diagrams предлагается «Fit T per class». Эталонный код и формат D5 поддерживают одно число температуры на scorer-kind, а per-class scaling не является тем же самым scalar temperature scaling и может изменить порядок logits.

**Лучший вариант для v1:** оставить только scalar T, как уже делает код. Если после реальных R-CAL/R-ACC эта калибровка не проходит CA-4/EV-7, исследовать vector/per-class calibration отдельным экспериментом, определить формат D5, тесты и повторно пройти приёмку. Не оставлять незапрограммированную опцию как будто она входит в текущую спецификацию.

Также полезно усилить проверку D5 при загрузке: обязательные scorer-kind, направления и length buckets должны присутствовать все; pi_train должен иметь ровно три конечных положительных значения; все температуры и пороги должны быть конечными. Сейчас проверка, проходящая только по существующим ключам словаря, может не заметить отсутствующую таблицу ngram, пока не произойдёт fallback к baseline.

## 5. Не оптимизировать CNN до появления релизных измерений

Текущий CNN мал, есть статистический baseline, а EV-12 не позволяет выпускать нейросеть без доказанного выигрыша. Это хорошая оптимизация затрат и рисков. Более крупная сеть, ансамбль, дистилляция или INT8 сейчас добавят работы без подтверждённой пользы.

До измерений на M1 Max и Windows важнее разложить end-to-end время на этапы:

1. callback события и обновление буфера;
2. gate/focus resolution;
3. словари и baseline/CNN;
4. чтение текста перед заменой;
5. сама замена;
6. read-back и проверка;
7. задержки при быстром вводе и вмешательстве пользователя.

Замеры CNN на облачном CPU не отвечают на главный вопрос пользовательского опыта — задержку всего решения и записи. И если большая часть времени приходится на Accessibility/UI Automation, оптимизация свёрток почти ничего не даст.

## Что я **не** рекомендую менять

- **Не увеличивать модель** без результата на R-CAL/R-ACC.
- **Не снижать пороги** ради recall до того, как пройдёт EV-1.
- **Не добавлять сложный ансамбль** до доказанного преимущества над baseline.
- **Не внедрять адаптивные пороги в v1**: отложенное решение разумно, потому что усложняет приёмку и может самоподдерживать ошибочную серию.
- **Не возвращать коррекцию на Enter/Tab** в observe-only архитектуру: это потребовало бы задерживать события, а текущая спецификация сознательно от этого отказывается.
- **Не обещать работу во всех приложениях**: allowlist только после успешных тестов на конкретном приложении — сильное решение, его нужно сохранить.

## Рекомендуемый порядок действий

| Приоритет | Действие | Зачем |
| --- | --- | --- |
| P1 | Уточнить M2 и гарантию отката; автоматический режим только там, где критерий восстановления реально выполняется | Сохранность текста важнее охвата |
| P1 | Исправить G2: proxy-gate отдельно от релизного EV-1/EV-12 | Не выдавать синтетические результаты за доказательство реальной безопасности |
| P1 | Фиксировать точный Windows layout ID; сделать spike Raw Input vs WH_KEYBOARD_LL | Избежать неверных отображений и повысить устойчивость наблюдателя |

| P2 | Добавить обработку отказа/отключения event hook и измерять каждую фазу отдельно | Надёжность и отладка важнее оптимизации микросекунд сети |

## Итоговый вердикт

У текущего подхода есть хорошие инженерные основания; полной переработки не требуется. **Главная потенциальная оптимизация — не модель, а контракт между наблюдателем клавиатуры и механизмом изменения текста.** Если безопасность текста остаётся главным требованием, автоматическую замену нужно строго ограничивать интерфейсами, которые можно проверить и восстановить. Если продукт должен работать почти везде, придётся принять более слабую гарантию для части приложений или инвестировать в нативные текстовые интеграции.

Остальное — улучшения конкретности и надёжности, а не повод усложнять ML-часть.
