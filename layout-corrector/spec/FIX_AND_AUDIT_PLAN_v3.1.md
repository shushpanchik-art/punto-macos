### Редакция 1.1 → 1.2 (вторая внешняя проверка, коммит `16bc251`)

Источники проверены повторно в основной сессии (`audit/L4_platform_api_audit.md`). Решения:

| № | Замечание | Решение |
|---|---|---|
| Q-1 | KLID нужно получать для потока целевого приложения, `GetKeyboardLayoutName` не годится | Подтверждено первоисточником: функция возвращает имя «for the calling thread». Решение в WP-2: раскладка идентифицируется по HKL потока **переднего окна** (`GetKeyboardLayout(idThread)`) и **отпечатку**, посчитанному `ToUnicodeEx` с `dwhkl` = этот HKL; KLID только диагностика. Не документировано, что чужой HKL принимается как `dwhkl` и что `GetKeyboardLayout` работает между процессами (источник говорит «the thread to query»): спайк S-2, при отказе пара OFF |
| Q-2 | Сценарий гонки M2 не учитывает, что один вызов `SendInput` не перемежается | Подтверждено: «These events are not interspersed with other keyboard or mouse input events inserted either by the user … or by calls to keybd_event, mouse_event, or other calls to SendInput.» Матрица отказов исправлена: окно гонки — **между чтением и записью** и фокус/изменение текста приложением; для Windows M2 одним вызовом, для macOS (`CGEventPost` по событиям) вмешательство возможно. Добавлены сценарии: частичное выполнение массива (число вставленных событий меньше запрошенного), отказ UIPI (ни возврат, ни `GetLastError` его не указывают), физически нажатый модификатор (документ: уже нажатые клавиши «might interfere»; проверка `GetAsyncKeyState`, отказ `modifier_down`), смена фокуса до и во время доставки |
| Q-3 | `ValuePattern.SetValue` не равно `REPLACE_RANGE` | Подтверждено: страница описывает «Sets the value of the element», замену диапазона и сохранение каретки не гарантирует. Введена таблица «класс контрола × результат записи» с пятью исходами (полное значение можно установить; диапазон можно заменить; каретка и выделение сохраняются; чтение есть, записи нет; интерфейса нет). `REPLACE_RANGE` присваивается только при втором и третьем исходах вместе с проверенным откатом |
| Q-4 | WP-4 («OFF») противоречит 13.5 строка 6 (fallback на другой скорер) | Единая политика: пакет LFC1 один на оба скорера, повреждённый пакет отклоняется **целиком**, `Engine` не создаётся. Движок не активен, поэтому нет и автокоррекции; ручная конвертация (20.8) калибровки не требует, поэтому режим `MANUAL_ONLY`, а не `OFF`. Fallback «другой скорер» из строки 6 удаляется. Прежний валидный пакет остаётся при неудачном обновлении (строка 12). Тест проверяет: исключение, отсутствие `Engine`, режим `MANUAL_ONLY` |
| Q-5 | WP-6: интервал для `w`, а D5 хранит скаляр | В D5 хранится `w_ship` = нижняя граница двустороннего 90% интервала (бутстреп по пользователям): консервативное для ложных исправлений. Точечная оценка и верхняя граница хранятся рядом как справка. EV-1 — по `w_ship`; EV-1 при точечной оценке и верхней границе — стресс-отчёт, не ворота |
| Q-6 | L6: сценарий 5e-5 без критерия | 5e-5 помечен **диагностическим** (доля принятий публикуется, критерия нет: точка правила 4.8e-5 лежит рядом). Обязательные сценарии: 2e-4 (ложное принятие), 2e-5 (мощность) |
| Q-7 | L3: фаззинг эталона не доказывает доставку физических событий hook или Raw Input | Принято: L3 доказывает свойства **алгоритма эталона** (статус `REFERENCE_VERIFIED`). Доставка физических событий — `INTEGRATION_VERIFIED`: тест RT-16 на реальных устройствах (генератор реальных нажатий, сравнение счётчика hook и счётчика Raw Input, 10⁶ событий, потеря 0) |
| Q-8 | L4: добавить `listenOnly`, `CGEventTapEnable`/`IsEnabled`, `CGEventTapLocation`, область Secure Event Input, статус `UCKeyTranslate`, `TISCopyCurrentKeyboardLayoutInputSource`, `RegisterEventHotKey`, `SMAppService` | Внесено в L4 и в 13.7: tap только `listenOnly`, место `kCGSessionEventTap` (HID-точка требует root: заголовок CGEvent.h); Secure Event Input — глобальный сигнал без атрибуции процесса (Apple TN2150): DENY, пока он включён; `UCKeyTranslate` и `NSEvent.characters(byApplyingModifiers:)` сравниваются спайком S-6; источник ввода, не являющийся раскладкой, → OFF; `RegisterEventHotKey` — декларация из названного SDK и тест регистрации |
| Q-9 | Карточка на каждый API | Формат отчёта L4: таблица «заявление → вердикт → цитата → что говорит ТЗ → тест (S-n или RT-n)» |

Дополнительно по замечаниям проверки: безопасная политика crash dump и проверка отсутствия снимка Undo в дампах вынесены в WP-5 и L9; формальные правила оценки `w` (какие события, какой знаменатель, анализ чувствительности) вынесены в WP-6; точная нормировка `pi_train` с допуском вынесена в WP-8; исследование Text Services Framework перенесено в список будущих экспериментов и не блокирует v3.1.

## Принцип закрытия замечаний (четыре статуса)

Замечание закрыто **на уровне**, а не «закрыто вообще». Каждое имеет явный статус и доказательство:

| Статус | Что он означает | Доказательство |
|---|---|---|
| `TEXT_FIXED` | Исправлено в нормативной прозе ТЗ | Цитата нового текста и запись в `CHANGELOG_v3.1.md` |
| `REFERENCE_VERIFIED` | Эталонный код, схемы и векторы прошли воспроизводимые проверки | Команда, вывод, хеш файлов в `audit/` |
| `INTEGRATION_VERIFIED` | Реальный адаптер проверен на целевой ОС и приложениях | Отчёт запуска на устройстве. **В облаке недостижим** |
| `RELEASE_GATE_PASSED` | Выполнены реальные требования приёмки и безопасности | Протокол ворот. **В облаке недостижим** |

Цель этой работы: все A-/O-замечания не ниже `REFERENCE_VERIFIED` там, где это применимо к спецификации и эталонному коду; для остальных — `TEXT_FIXED` плюс протокол, критерий и ответственный. Описание будущего теста **не** считается его выполнением: оно даёт `TEXT_FIXED`, но не `REFERENCE_VERIFIED`. Положительный итог аудита означает «спецификация v3.1 внутренне согласована и проверена», а не «продукт готов к production».

## Часть B. Генеральный аудит и итоговая проверка

Идея: «свежие глаза». Каждая линия выполняется агентом, который не видел моих исправлений, получает только ТЗ и критерий прохождения и обязан приложить доказательство (вывод скрипта или цитаты со строками). Находки: P0/P1/P2; после исправлений линия повторяется (максимум 2 раунда).

| Линия | Что проверяет | Метод | Критерий прохождения | Исполнитель |
|---|---|---|---|---|
| L1 Слепая реимплементация | Однозначность прозы | Агент получает ТЗ без блоков кода 20.x, с таблицами и векторами, пишет движок на Node.js, прогоняет векторы. ### Матрица отказов транзакции замены (L3/L9, WP-1)

Эталонная модель: `SimField` (текст, каретка, окно приложения) и функция транзакции из 20.14 с точками отказа. Ожидаемое поведение задано таблицей **до** прогона.

| Фаза транзакции | Отказ | Ожидаемый исход | Безопасное состояние |
|---|---|---|---|
| заморозка буфера | потеря фокуса | отмена, замены нет | поле не менялось |
| гейт | гейт стал `DENY`/`UNKNOWN` до записи | отмена | поле не менялось, буфер сброшен |
| чтение диапазона | прочитанный текст ≠ ожидаемому | отмена | поле не менялось; M1: счётчик отказов приложения |
| запись | частичная запись | откат до исходного | `RESTORED`; иначе `UNRECOVERED` и карантин |
| запись | таймаут | откат | то же |
| запись | авто-исправление приложением | сверка read-back не проходит → откат | `RESTORED` / карантин |
| проверка | read-back ≠ ожидаемому | откат | `RESTORED` / карантин |
| откат | сам откат не прошёл | `UNRECOVERED` | карантин приложения, запись инцидента без текста |
| между чтением и записью | пользователь печатает (конкурирующий ввод) | M1 с `ROLLBACK`: чтение диапазона после записи не совпало → откат; M2: отмена (`typed_ahead`) | M2 недопущен к AUTO |
| запись M2 | частичная вставка (вставлено меньше событий, чем запрошено) | исход определяется чтением: `RESTORED` или `UNRECOVERED` | ручной режим помечает инцидент, приложение в карантин |
| запись M2 | отказ UIPI (возврат и `GetLastError` его не указывают) | read-back не совпал → `RESTORED` | приложение в карантин |
| запись M2 | физически нажат модификатор | отмена `modifier_down` до записи | поле не менялось |
| запись M2 (Windows) | пользователь печатает во время одного вызова `SendInput` | документально не перемежается; тест подтверждает на устройстве | `INTEGRATION_VERIFIED` |
| любая | отказ или отключение hook | буфер сброшен, коррекция остановлена | режим ≤ `MANUAL_ONLY` до проверки канарейкой |
| любая | отзыв разрешения ОС | то же | `OFF` для приложения |
| любая | смена раскладки или отпечаток не совпал | отмена | `OFF` для пары до подтверждения |

Инвариант матрицы: ни в одной ячейке `convert` не завершается молча после несовпадения read-back; ни в одной ячейке AUTO не продолжается на основании неполного потока событий.

### L6: предрегистрация (записана до запуска, не подбирается по результату)

* Правило, которое проверяется: EV-1 принято ⇔ `n ≥ 10⁵ ∧ users ≥ 20 ∧ docs ≥ 100 ∧ точечная оценка ≤ 4.8e-5 ∧ консервативная кластерная верхняя граница ≤ 1e-4`.
* Сценарии (по 10 000 прогонов каждый): истинная частота 2e-4 (должно отвергаться), 1e-4 (граница, диагностика), 5e-5 (диагностика: доля принятий публикуется, критерия нет), 2e-5 (должно приниматься с мощностью ниже); пользователей 20 / 50 / 200; кластеризация: без кластеров, умеренная (отрицательное биномиальное с параметром дисперсии 2), сильная (дисперсия 10; 2% пользователей дают 50% ошибок).
* Seed: `1000 + индекс прогона`, фиксированы в скрипте; результаты воспроизводимы.
* Генерация: пользователи с логнормальным числом слов; документы внутри пользователя; ошибки — по процессу Пуассона с гамма-смешанной интенсивностью на уровне пользователя и документа.
* **Критерий ложного принятия:** при истинной частоте 2e-4 доля принятий ≤ 5% (верхняя граница Клоппера-Пирсона 95% на эту долю ≤ 7%) во **всех** сценариях кластеризации.
* **Критерий ложного отказа (мощность):** при истинной частоте 2e-5 доля принятий ≥ 80% при умеренной кластеризации и числе пользователей ≥ 50, `n = 10⁵`. Если не выполнено, критерий не отвергается, а в ТЗ вписывается минимальный объём `n`, при котором мощность ≥ 80% (находится той же симуляцией).
* Неопределённость самой симуляции: доли с доверительными интервалами Клоппера-Пирсона по 10 000 прогонов; результаты таблицей в раздел 18.
* Сначала критерии, потом запуск. Любое изменение правила или сценариев после запуска фиксируется в журнале как отклонение с причиной.

### Условия «готово» (Definition of Done) для v3.1

1. Открытых P0 и P1 нет; каждое A-/O-/P-замечание имеет статус не ниже `REFERENCE_VERIFIED` там, где это применимо, остальные — `TEXT_FIXED` плюс протокол, критерий и ответственный в явном списке.
2. Все линии L1–L9 пройдены, находки закрыты или перенесены в явный список «отложено» с причиной.
3. Репозиторий и документ совпадают (L7) побайтово после нормализации; JSON векторов идентичен при всех 10 seed.
4. Каждая линия имеет отчёт в `layout-corrector/audit/` с командами запуска.
5. `audit/MANIFEST.sha256` построен на полном commit SHA редакции.

### Что невозможно закрыть в облаке (честный список релизных блокеров)

`INTEGRATION_VERIFIED` и `RELEASE_GATE_PASSED` недостижимы здесь для: реальных `R-CAL` / `R-ACC` и итоговых EV-1 и EV-12; сквозных замеров на M1 Max и Windows; реализации и проверки адаптеров ОС на каждом приложении из матрицы поддержки; фиксации хешей корпусов при загрузке и проверки лицензий; спайка Raw Input против `WH_KEYBOARD_LL`; проверки политики crash dump на устройстве. Для каждого пункта в ТЗ v3.1 останется протокол, критерий и ответственный, но не результат.
