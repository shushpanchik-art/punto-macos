# AP-7 / RT-19: readings that are NOT agreed (status: OPEN, waiting for the requester)

Nothing below is a decision. The code follows the first option of each item only so that it can be tested; every item can be switched by a small change.
Specification: `spec/TZ_layout_correction_v3.md` (clause texts quoted exactly).

## 1. What is a "crash" that gives MANUAL_ONLY
Clauses:
* Failure row 11 (13.5): "An unhandled exception in the worker | The current word is KEEP; the worker restarts once; a second failure within 60 seconds gives MANUAL_ONLY | A notice after the second failure".
* AP-7: "A supervisor restarts the engine after a crash; two crashes within 60 seconds give MANUAL_ONLY (failure row 11)."

Gap: row 11 counts WORKER failures (inside one process). AP-7 says "engine" and "crash" and points to row 11. The text does not say whether a process crash and a worker failure share one count.

| Option | What it means | Consequence |
| --- | --- | --- |
| A (in the code now) | Two separate 60 s windows: worker failures (in-process, `lflifecycle.Supervisor`) and engine process crashes (`lfsupervisor.ProcessSupervisor`). One of each within 60 s is NOT MANUAL_ONLY | Simple; no channel between engine and supervisor. A worker failure followed by a process crash 10 s later restarts in AUTO although two failures happened inside 60 s |
| B | One shared window counting both kinds | Needs a channel from the engine to the supervisor (exit status, pipe) that carries a worker-failure time, because counters are not persisted (RT-6, AP-5). More code and one more interface to test; matches "(failure row 11)" most literally |
| C | Row 11 is worker-only; AP-7 asks only that the supervisor restarts the engine | No process-crash count at all: a process that crashes at start would be restarted forever unless some limit exists (see 3) |

## 2. How "MANUAL_ONLY" survives a process restart, and who tells the user
* The text gives no mechanism. The code passes `--manual-only` to the restarted engine; the flag lives only in the supervisor's memory (nothing is written to disk, consistent with RT-6 and AP-5 which forbid persisting incident counters).
* Consequence: if the supervisor itself dies, the latch is lost. Alternative: no flag, the engine asks the supervisor through a channel (more code).
* The notice kind `manual_only_after_crashes` is MY name; row 11 says only "A notice after the second failure". It is not in the notice table of 13.5/AP-8 (check and register, or reuse the existing worker notice).

## 3. Extras not in the specification (each one is an added requirement; marked so in the code)
| Extra | Why it exists | Consequence if removed |
| --- | --- | --- |
| Minimum pause of 1 s between starts | Prevents a tight restart loop | Restarts as fast as the OS allows |
| Crash-loop guard: more than 5 crashes in 10 min: supervisor exits with status 70 | Prevents an endless loop with a permanently broken engine | The loop runs forever; or the guard is replaced by C above |
| After "gave up" nothing runs | Consequence of the guard: AP-2 (an icon that always shows a state) cannot be met by a process that is gone | Needs a decision: who shows "Off" after the supervisor gave up |
| Child streams are the null device | RT-6: nothing typed in any log | none (it follows RT-6) |

## 4. Autostart mechanism (clause: platform table, "Autostart | Per-user startup entry | Login item (`SMAppService`, macOS 13+)"; AP-7: "Starts at login (a setting)"; AP-6: "removes ... its login item or startup entry")
* Windows: "per-user startup entry". The code generates the per-user `Run` value. Another valid per-user entry is a shortcut in the Startup folder. The `Run` key behaviour is NOT verified against Microsoft documentation in this repository.
* macOS: the text says "Login item (`SMAppService`)". The literal reading is `SMAppService.mainApp` (the app opens at login, no property list at all). The code generates an agent property list (`SMAppService.agent`, `KeepAlive`, `RunAtLoad`): that is an extension, it adds restarting of the SUPERVISOR itself, which the text does not ask for ("a supervisor restarts the engine", not "something restarts the supervisor").
  * Option mainApp: no plist; the main executable runs `--supervisor`; nothing restarts a dead supervisor.
  * Option agent (code now): plist, launchd restarts the supervisor after a non-zero exit; registration is native (SMAppService), not possible from Python, NOT RUN.
* The "start at login" setting (AP-4) is the switch for either; `start_at_login` exists in the store (default True); registering and unregistering are not written.

## 5. RT-19 (one instance per user session)
Clause: "The tool MUST run as at most one instance per user session. A second start MUST exit at once (a per-session lock held by the first instance), and when the lock cannot be established the engine MUST stay OFF. ... Test: start two copies, type 1,000 words that are converted; there is exactly one replacement per word and no UNRECOVERED outcome."
* Windows backend: named mutex in the `Local\` namespace, which is per session (written, compiled only).
* POSIX backend: a file lock in a per-user directory. That is per USER, not per login session. Divergence from the clause where one user has several sessions at once; option: a per-session directory (for example the per-user temporary directory of the session), which the OS adapter would have to supply.
* The second start exits with status 0 (not an error). The text says "exit at once" only.
* Several supervisors: a second supervisor's engine exits at once with status 0, which the supervisor treats as a clean exit, so it ends too. If the first engine crashes and the second supervisor's restart wins the lock first, the first supervisor's restart ends: one instance remains in either case.
* The 1,000-word test on two real instances is NOT RUN (needs a real OS and a real hook); the portable tests check the lock, the decision and that the engine without the lock converts nothing.

## 7. AP-8 notifications (portable part, `app/lfnotify.py`): gaps and my readings, not agreed
Clauses: 13.5 "A notice is shown at most once per cause and per 24 hours, and never takes focus."; AP-8 "Non-blocking, never take focus, rate-limited as in 13.5; each offers one action (open settings, re-enable)"; row 10 "After UNRECOVERED the notice says that the field may differ from what was typed and that the application's own undo is the way back"; rows 8 and 14 "the way to restore the permission" / "names the permission".
* **Priorities: the specification defines none.** Nothing is invented: delivery is first come, first served. If priorities are wanted (for example an UNRECOVERED incident before a settings notice), the requester must say which order.
* "Cause": I use the notice kind, and for incidents also the outcome (restored or unrecovered), so a later UNRECOVERED incident is never hidden by a RESTORED one shown a moment ago. The text could also mean one cause per application; then an incident in another application within 24 h would show again.
* The boundary: two shows exactly 24 h apart are allowed (86,400,000 ms inclusive); closer is refused; a clock that went backwards opens no slot. The text does not say which.
* The 24 h memory lives in the process only. After a restart a notice can show again within 24 h; persisting it would add a stored timestamp (AP-5, RT-6 say nothing about it).
* The action of each kind is mine except where the text implies it: row 10 re-enable, rows 8 and 14 open settings. Rows 9 and 13 use re-enable ("until the user re-enables AUTO"); the others use open settings. AP-8 says "each offers one action": a notice without an action is refused.
* The runtime has one flag `models_ok`, so rows 3 to 6 and 12 cannot be told apart: one kind `models_unavailable`. Row 3's "one-time notice that the basic mode is in use" and row 7's icon text ("layout not supported", an icon, not a notice) are not produced.
* Kinds that are not in the table at all: `manual_only_after_crashes` (AP-7), `instance_lock_unavailable` (RT-19), the settings and store notices (`settings_not_saved`, `autostart_failed`, hotkey, `cipher_unavailable`, `file_unreadable_defaults`, `newer_file_kept`): shown through the same limit. "Re-enabled" (the user's own action) and "migrated" produce no notice.
* No wording: a notice has a text identifier; the words, their translation and the display (non-blocking, no focus) belong to the interface and are NOT RUN. A failing display is retried up to 3 times (my number) and then dropped and counted.
* The notice of an incident carries the opaque identifier of the application for the re-enable action; it is the identifier the user already sees in the application list.

## 8. AP-2 status and pause (portable part, `app/lfstatus.py`, `Runtime.set_paused`): my readings, not agreed
Clause AP-2: "A menu-bar or tray icon always shows one of Active, Paused, Manual only, Off. One click pauses (the gate becomes DENY, so nothing is recorded). "Pause for this application" adds it to the application list". AP-1: "Until all are granted the state is OFF and the status icon names the missing permission."
* Precedence is not defined. Mine: a missing permission or a missing instance lock shows Off even while paused (so the icon can name the permission); otherwise Paused wins over a per-application Off or Manual only; no focused application is Off with the reason `no_focus`.
* While paused the gate is DENY whatever the adapter reports (the adapter cannot lift the pause, a focus change does not either); resume restores the LAST verdict of the gate (ALLOW, DENY or UNKNOWN) without a new adapter call; pausing and resuming drop the word in progress.
* "Pause for this application" is the blacklist entry of AP-4 (the re-enable button undoes it); the confirmation notice "re-enabled" is not shown (section 7).
* The state is in memory only: a restart is not paused.

## 9. AP-11 diagnostics (portable part, `app/lfdiag.py`): OPEN questions and my readings, not agreed

## 10. Settings Reset and Delete all data versus the start-at-login registration (AP-4/AP-5), fixed
Defect found on 7294dfc: after a successful `set_start_at_login(False)`, `Reset` stored the default (True) without calling the adapter. Now `Reset` calls the adapter and takes the default only if it answered exactly True; a missing or failing adapter leaves the real value and reports `autostart_failed`; `Delete all data` never registers or unregisters anything, so `start_at_login` keeps the real value there (after the files are gone, the next start reads the default; making a start reconcile the stored value with the system needs an adapter query, not written). A failing removal in `Delete all data` is reported as `delete_failed`.

Clause AP-3: "Detected from the installed input sources, where supported means that the fingerprint equals the table (13.7): when exactly one supported English layout and one supported Russian layout are installed, that pair is used; otherwise the user chooses; an unsupported variant switches the tool off for it with the notice of failure row 7". ## 13. AP-9 updates (portable part, `app/lfupdate.py`): OPEN questions, not agreed
Clause AP-9: "Application, model, lexicon and calibration package are signed and versioned (DP-7). A new package is switched in only at restart or when no word is in progress; staged rollout; one-step rollback; a failed verification keeps the previous package (failure row 12)". DP-7: signed, versioned, carries the hash of the calibration package, supports one-step rollback. Row 6: a failed update leaves the previous valid package active.
* **Package format and signature.** The specification fixes neither the manifest, nor the signature scheme, nor the keys, nor where packages come from. Here: a manifest with `version`, `rollout_percent` and a `sha256` per component, canonical JSON bytes, and an injected `verify(bytes, signature)` that must answer exactly `True`. No cryptography is written here. The real scheme (and whether the application itself is replaced by the OS installer or by this mechanism) is open.
* **Components.** A package is a non-empty subset of application, model, lexicon, calibration; a package with a model must carry the calibration hash (DP-7, row 6). Whether every update must carry all four is open.
* **Version rule.** Three integers; a package must be newer than the active one (replay and downgrade protection); the only way back is the rollback. Not in the text.
* **"No word is in progress".** Read as: nothing being recorded and no undo, toggle or manual conversion in flight. A switch drops the undo snapshot of the previous word if the engine is rebuilt; whether that is acceptable is open.
* **Staged rollout.** Read as `bucket < rollout_percent` with a bucket in 0..99 that the adapter supplies. The text names no bucket; a persistent per-device identifier would be a privacy decision (13.4) and is not made here. A package the rollout has not reached is neither stored nor reported.
* **One-step rollback.** To the previous package, or to the built-in one after the first update. The package rolled back from is deleted and its version blocked (at most 16 kept) so that a feed cannot bring it back at once; a second rollback does nothing. Whether a rollback may be undone (toggle) and for how long a blocked version stays blocked are open.
* **Failure notice.** Row 12 says "a notice"; kind `update_failed`, one action (open settings), one cause for the 24 h limit whatever the failure code. The codes (`signature`, `hash`, `shape`, ...) are kept in counters and the log, never shown.
* The 10 MB limit is the "whole package" budget of the table at 978 ("not yet assembled"); it is used as a bound here, not asserted as normative.
* Not written: download, transport security, the real signature check, the swap of the application, the real restart, the user interface of the update and rollback buttons. NOT RUN.

## 14. AP-6 uninstall (portable part, `app/lfuninstall.py`): OPEN questions, not agreed
Clause AP-6: "A signed installer or package, per user and without elevation where the OS allows. The uninstaller removes the application, its login item or startup entry and, on request, all user data, and leaves no hook or helper process running". AP-5: "Delete all data" removes settings, exceptions and diagnostics.
* **Order.** The text lists no order. Here: startup entry, processes, application, data, final check. The startup entry goes first so that nothing starts again if a later step fails; the data goes last and only after no process is left, because the engine saves its state when it ends (`lflifecycle.stop`), which would bring deleted data back.
* **"Leaves no hook or helper process running"** is read as: asked to end, and the list is read again, in at most 5 rounds with 200 ms between (my numbers, not normative). A process list that cannot be read or a failing query is `unverified` and the result is incomplete: the text does not allow the claim "none left" without a check. Whether the uninstaller may force an end after the rounds (the supervisor's watchdog does, for the engine) is open.
* **Nothing is deleted while a process may still run** (application and data). On Windows an open file cannot be deleted anyway; on macOS it could, but then a running helper would be left without its application. A reading in which the application is removed regardless is possible.
* **"On request"** is read as a flag the user sets; the default is that data stays. The exception list is encrypted with the OS key store (13.3): whether the uninstaller must also remove the key store entry is open (the portable store has no such entry; `Store.delete_all` removes the files only).
* **Diagnostics** live in memory only here (AP-11 reading), so there is no file to remove for them.
* **Partial data removal** (a link or a directory that has the name of one of the store's files is never followed or removed) makes the result incomplete and the leftover is named by a code, not by a path.
* **Per user, without elevation** is a property of the installer and is not written.
* Not written: the installer, the signed package, the real removal of the application files and of the real startup entry, the real process list and stop. NOT RUN.

## 15. AP-10 accessibility of the tool's own interface: BLOCKED on a decision, nothing implemented
Clauses: AP-10 "The settings, the notices and the status icon work with VoiceOver and NVDA, and a correction is not announced twice (14.4)"; 14.4 "Screen readers: No change announced twice; test with VoiceOver and NVDA. A silent text replacement can be invisible or noisy for assistive technology".
* **Who announces?** Two readings: (A) the tool announces nothing about a correction and only makes sure that the replacement is one operation, so the screen reader announces the changed text once (M1 is one operation; M2 is a series of key events and may be announced per character); (B) the tool announces a correction itself (a short statement) and must suppress its own repetition and any double with the screen reader's own announcement. The first fits "a silent text replacement can be invisible" less well, the second adds an output the specification does not describe (no text, no identifiers). The choice changes the design and cannot be made from the text.
* Under (B) the portable rule would be: one announcement identifier per transaction, never repeated for the same transaction, none for ABORTED, one for an undo. That is a few lines and is NOT written until (A) or (B) is chosen.
* Labels, roles and focus order of the settings, the notices and the icon belong to the real user interface, which is not written. VoiceOver and NVDA runs are NOT RUN.
* **One prompt at a time, also across a revoke (defect found and fixed after c4565e1).** The first version asked only whether the CURRENT permission already had an open prompt. With Input Monitoring granted and the Post Event prompt open, a revoke of Input Monitoring made it current again and a second press opened a second prompt. Now a single prompt may be open whichever permission it is for; a press while one is open is a duplicate; the view shows the prompt that is really open (`prompt_for`) and what comes next (`next`). A late answer (`on_answer`) counts only for the open prompt, `granted` only when the status agrees. After a quit and resume the open prompt is kept; a restart of the process cannot know about a prompt the OS still shows (open: whether the adapter can report it).

### Added after the audit of AP-9 and AP-6 (sections 13 and 14), my readings, not agreed
* **AP-9: the stored package is not trusted because this module wrote it.** The manifest and its signature are kept next to the components and are checked again, with the hash of every file, when the staged package is switched in, when the module starts and when a rollback would activate the previous package. A mismatch drops a staged package (row 12 notice, code `integrity`), replaces a damaged active package by the previous one when it verifies, else by the built-in one, and sends a rollback to the built-in package. Alternative: verify only when staging (faster, but a change made on disk in between would be used).
* **AP-9: an unreadable state file** keeps the package directory aside as `packages.bad` together with `state.json.bad` instead of deleting it (the next such event replaces it).
* **AP-6: order of the irreversible step.** The user data is deleted only when the application is removed or already absent. If the application cannot be removed, the uninstall is incomplete and the data stays, so that a still installed application does not lose the user's data. The other reading (delete the data the user asked for in any case) is open.
* **AP-9 fault injection (after b90f53f), my readings, not agreed.** (1) Moving the packages of an unreadable state aside is done before the unreadable state file is moved, an existing aside copy is deleted only after the new one is in place (otherwise the new copy stays as `packages.bad.tmp` and the old one as it was), and when the packages cannot be moved nothing is deleted and the updater is *frozen*: it refuses to store anything (status `storage`) until a later start succeeds. Confirmed defect on b90f53f: a failing move deleted the packages AND the existing aside copy. Alternative to freezing: continue with the built-in package and leave the directory alone (storing new packages would then need a second location). (2) A failing write in the drop of a staged package (integrity or validation branch) leaves the state as it was and the status is the reason (`integrity`, `validation`); the failure is only counted (`drop_failed`), and the next try refuses again and drops. Confirmed on b90f53f: the failure raised out of the switch. (3) Limits of the link check, stated carefully: refused are a link in place of the package directory, of `manifest.json` and of a component; NOT covered are a hard link with identical content, a link above the package directory (the root or `packages` itself), a bind mount, other users' write access, and a change made between the check and the later use of the files (no file lock). Confirmed on b90f53f: a package directory that was a link to a valid copy was switched in.
* **Store and crash report fault handling (after ac023f4), my readings, not agreed.** Confirmed defects on ac023f4, each with a regression test that fails there: (1) `Store.load` raised `OSError` when an unreadable file could not be moved aside (the start would crash); now the file is left where it is, the store is read-only (never written over) and the notices `file_unreadable_defaults` and `file_aside_failed` are recorded. (2) A backup copy that could not be written before a migration (disk full) was treated as a corrupt file and the old file was moved aside; now no migration is done, the old file stays intact and read-only, notice `migration_backup_failed`, the partial copy is removed. (3) A failing removal of an old crash report raised after the new report was written, so `handle` returned `None` and skipped the opt-in upload; now the new report is reported and uploaded. Whether a read-only store should instead keep working in memory with a warning to the user is open (it does: `save` answers False and the settings layer reports `settings_not_saved`).
